Estrategia Supabase: Cloud → VPS

Fase A — Sprints 1-4

Supabase Cloud (Desarrollo)

Usar plan Free o Pro ($25/mes) para validar DDL, RLS y desarrollo de API. Ventajas: setup instantáneo, GoTrue listo, dashboard SQL integrado. Correr init.sql directo contra la instancia cloud.

Fase B — Sprint 5-6

Preparar VPS Self-hosted

Montar PostgreSQL 16 + pgvector + pgBouncer (transaction mode) en VPS. Instalar GoTrue, PostgREST, Realtime, Storage vía Docker Compose. Migrar: pg_dump → pg_restore con roles y RLS.

Fase C — Sprint 7+

Producción Self-hosted

Toda la operación en VPS propio. Streaming replication al VPS de backup. Backups diarios automatizados. Cloudflare Tunnel para seguridad. Supabase Cloud queda como staging/QA.

# Migración Cloud → VPS
pg_dump -h db.xxxx.supabase.co -U postgres -d postgres \
  --schema=public --no-owner --no-acl > backup.sql

# Restaurar en VPS (previamente crear DB + extensiones)
psql -h vps-ip -U postgres -d omnichannel < backup.sql

# Verificar RLS
psql -h vps-ip -U app_user -d omnichannel -c "
  SET LOCAL app.current_client_id = 'test-tenant-id';
  SELECT count(*) FROM contacts;
"

Arquitectura de Agentes

El proyecto requiere 8 agentes base operando en sesiones de Claude Code/Cowork independientes, más roles secundarios que los agentes existentes asumen en momentos clave. En la práctica, 3 sesiones corren simultáneamente (Dev A + Dev B + 1 on-demand). Los restantes se activan por sprint o bajo demanda.

Orquestador Opus
Arquitectura, decisiones de diseño, PR review cruzado, resolución de conflictos, planificación de sprint. Tú (Miguel) ejecutas esta sesión.
Responsabilidades: ADRs en MEMORY.md, merge a main, code review con checklist de METHODOLOGY.md §7, deploy al VPS.
CLAUDE.md METHODOLOGY.md PROGRESS.md MEMORY.md
Activo: todos los sprints. Dedicado: revisiones de PR y decisiones clave.
Dev A — Foundations Sonnet
Capa de datos, modelos SQLAlchemy, schemas Pydantic, core services, infraestructura, AI state/graph, servicios fundacionales (RAG, providers, onboarding).
Loop semi-autónomo: implementar → pytest → ruff → commit → PROGRESS.md. Checkpoint cada 3-5 módulos.
app/models/* app/schemas/* app/core/* app/services/* app/agents/state.py app/agents/graph.py
Activo: Sprints 1-14. Siempre en paralelo con Dev B.
Dev B — Integration Sonnet
Middleware, endpoints API, Celery tasks, agent nodes, tests unitarios e integración. Consume los modelos/schemas de Dev A.
Usa stubs/mocks si Dev A no ha pusheado. Escribe tests para cada módulo. Loop idéntico a Dev A.
app/api/v1/* app/middleware/* app/tasks/* app/agents/nodes/* tests/*
Activo: Sprints 1-14. Empieza cuando Dev A pushea models/ y schemas/.
DevOps & Infra Sonnet
Docker Compose, Dockerfile, Traefik, CI/CD (GitHub Actions), scripts de deployment, Cloudflare config, monitoreo (Prometheus/Grafana).
Configura infraestructura. Mantiene docker-compose.yml. Actualiza CI pipeline. Prepara el VPS.
docker-compose.yml Dockerfile traefik/* .github/workflows/* scripts/*
Intensivo: Sprints 2, 8. On-demand: resto.
QA & Testing Sonnet
Test suites completos: unit, integration, e2e. Playwright para frontend (Sprint 15). Cobertura > 70%. Tests de aislamiento RLS en cada sprint.
Ejecuta pytest con coverage. Crea fixtures en conftest.py. Playwright codegen para e2e del frontend. Valida RLS cross-tenant.
tests/unit/* tests/integration/* tests/e2e/* tests/conftest.py playwright.config.ts
Al final de cada sprint. Intensivo: Sprints 8 (MVP e2e), 15 (Playwright).
Frontend Sonnet
Next.js 14+ App Router, TypeScript, shadcn/ui, Tailwind CSS, next-themes, next-intl (6 idiomas), Zustand stores, Supabase Realtime.
Scaffold del proyecto, componentes UI, páginas de admin, onboarding wizard, dashboard con Recharts, responsive mobile-first.
frontend/* frontend/app/* frontend/components/* frontend/stores/* frontend/i18n/*
Activo: Sprint 15 exclusivamente. Se puede dividir en 2 (scaffold + UI).
Documentación Haiku
Actualización de PROGRESS.md, generación de API docs (OpenAPI), docstrings, diagramas Mermaid, changelog por sprint.
Al cierre de cada sprint: actualiza progreso, genera docs del API, verifica docstrings Google-style, crea changelog.
PROGRESS.md MEMORY.md docs/* CHANGELOG.md
Al cierre de cada sprint. Haiku por eficiencia de costo en tareas repetitivas.
DB & SQL Sonnet
DDL, migraciones Alembic, optimización de queries, políticas RLS, configuración pgBouncer, índices, streaming replication.
Valida que toda tabla tenga client_id + RLS con FORCE. Revisa planes de ejecución (EXPLAIN ANALYZE). Crea migraciones Alembic.
supabase/init/* migrations/versions/* scripts/backup.sh scripts/replication/*
Intensivo: Sprints 1, 3, 5, 8. On-demand para migraciones.

En la práctica ejecuta máximo 3 sesiones simultáneas. Dos sesiones principales (Dev A + Dev B) y una rotativa entre DevOps, QA, DB o Docs según la etapa del sprint. Más sesiones simultáneas generan conflictos de merge y desperdician tokens en coordinación.

En lugar de crear más agentes simultáneos, los agentes existentes asumen roles especializados en momentos clave del sprint:

Prompts para Roles Secundarios

Security Auditor (pre-merge)
# Ejecutar en la sesión de Dev A o Dev B (el que NO es author del PR)

Actúa como Security Auditor para este PR.
Sprint activo: {NN}

1. Lee CLAUDE.md (reglas de seguridad absolutas)
2. Haz git diff main...feature/sprint-{NN}-{desc}
3. Verifica en CADA archivo cambiado:
   - SET LOCAL en todas las queries (nunca SET)
   - RLS policies con FORCE en tablas nuevas
   - Filtro pre-vectorial por client_id (nunca post-ranking)
   - pgcrypto en columnas sensibles (teléfonos, emails)
   - Sin secretos hardcodeados
   - AppException para errores (nunca tracebacks)
   - Sin sync I/O en contexto async
4. Reporta: PASS o lista de violaciones con archivo:línea
Performance Tester (post-sprint 8)
# Ejecutar en la sesión de QA Agent

Actúa como Performance Tester.
Sprint completado: {NN}

1. Lee los endpoints nuevos en app/api/v1/
2. Genera un script locust (locustfile.py) que simule:
   - 50 usuarios concurrentes, 5 tenants distintos
   - Flujo: login → crear contacto → enviar mensaje → consultar RAG
3. Identifica queries N+1 con EXPLAIN ANALYZE
4. Valida que el token_budget node degrade correctamente
   bajo carga (ok → degraded → exceeded)
5. Reporta: latencia p50/p95/p99, queries lentas, bottlenecks
Migration Reviewer (Supabase → VPS)
# Ejecutar en la sesión de DB Agent

Actúa como Migration Reviewer para la migración Supabase Cloud → VPS.

1. Verifica el dump: pg_dump -Fc --no-owner -h supabase-host
2. Revisa que todas las extensiones existan en el VPS target:
   pgvector, pgcrypto, pg_trgm, uuid-ossp
3. Valida RLS policies post-restore con 2 tenants de prueba
4. Verifica índices HNSW y GIN post-restore
5. Compara row counts entre source y target
6. Valida streaming replication si está configurada
7. Reporta: READY o lista de diferencias con fix

Plan de Ejecución Paralela

Cada sprint sigue este patrón de 3-5 días. Dev A arranca primero con los cimientos, Dev B empieza con stubs y transiciona a código real cuando Dev A pushea.

DíaDev A (Foundations)Dev B (Integration)On-Demand
1 Models, schemas, core services conftest.py, stubs, fixtures —
2 Servicios fundacionales → push Middleware, API endpoints (con stubs) DB: migraciones Alembic
3 Refinamiento, edge cases Celery tasks, agent nodes, reemplazar stubs QA: test suite inicial
4 PR → code review del PR de B Tests completos → PR → review del PR de A Docs: PROGRESS.md, changelog
5 Fix issues de review → merge a main → integration tests DevOps: actualizar Docker/CI

git checkout main

# Review del PR del otro dev
gh pr diff 42

Docker Compose

# Levantar todos los servicios
docker compose up -d

# Ver logs en tiempo real
docker compose logs -f app

# Acceso directo a PostgreSQL
docker compose exec postgres psql -U postgres -d omnichannel

# Rebuild después de cambios en Dockerfile

# Detener todo
docker compose down

Base de Datos & Migraciones

# Ejecutar DDL inicial
psql -h localhost -U postgres -d omnichannel -f supabase/init/init.sql
psql -h localhost -U postgres -d omnichannel -f supabase/init/phase2_tables.sql

# Alembic — crear migración
alembic revision --autogenerate -m "add_agent_action_logs_table"
alembic upgrade head
alembic downgrade -1
alembic history --verbose

# Verificar RLS (siempre con app_user, nunca superuser)
psql -h localhost -U app_user -d omnichannel -c "
  BEGIN;
  SET LOCAL app.current_client_id = 'tenant-a-uuid';
  SELECT count(*) FROM contacts;  -- solo ve datos de tenant A
  ROLLBACK;
"

# Backup manual
pg_dump -h localhost -U postgres -d omnichannel \
  --format=custom --compress=9 > backup_$(date +%Y%m%d).dump
pg_restore -h localhost -U postgres -d omnichannel_test backup_20260903.dump
